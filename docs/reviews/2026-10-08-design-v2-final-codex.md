- 대상: `docs/superpowers/specs/2026-10-08-jev-chat-design.md` v2 전체. 이하 `설계:L`은 이 파일의 행 번호다.

## 최종 의견: No-Go

**현재 v2를 확정 계약으로 삼아 구현 계획으로 넘어가는 것은 No-Go다.** 수락 순번·완료 순번·재연결, 실패 요청 재전송, 큐 예약, 평가 합격 판정에 서로 다른 구현을 유발할 Major 문제가 남아 있다. 분산 큐나 새로운 서비스를 추가할 필요는 없다. 아래 F1~F6의 규칙을 일관되게 확정한 뒤 구현 계획으로 넘어가면 된다. 나머지 지적은 구현 계획의 작업·검증 조건에 반영할 수 있다.

판정은 **해소 8건 / 부분 10건 / 미해소 0건**이다. “해소”는 설계상 요구가 충족됐다는 뜻이며 구현 검증 완료를 뜻하지 않는다. “부분”은 보완이 있으나 기존 문제의 일부 또는 보완 과정의 모순이 남았다는 뜻이다. `[R#]` 표기의 존재만으로 해소 판정하지 않았다.

## 잔여 및 신규 지적

### F1. Major · 수락 순번·대화 순서·완료 동기화 커서가 같은 seq로 혼용됨 [R9][R10]

- **위치:** 설계:59, 70, 78~82, 199~202, 212~213, 238~248
- **문제:** user를 수락할 때 seq를 정하면서 assistant에도 세션 내 유일 seq가 필요하다. `beforeSeq` 이력과 `afterSeq` 복구가 이 순번을 공유하면 순차 처리와 재연결을 모두 만족시키기 어렵다.
- **근거:** 추론 예시: U1을 seq=1, 대기 U2를 seq=2로 수락한 뒤 A1을 다음 seq=3에 저장하면 U2의 `loadContext(beforeSeq=2)`는 직전 완료 A1을 제외한다. done의 seq가 user seq=1이면 이미 U1을 본 클라이언트의 afterSeq=1 뒤로 완료가 들어가지 않는다. done이 assistant seq=3이면 ack/status와 seq 의미가 달라진다. 현재 어느 규칙인지 정해지지 않았다. 동기화 최대 50개에도 다음 커서·hasMore가 없다.
- **제안:** 단순 MVP에서는 요청별 `turn_seq`를 예약하고 user/assistant는 `(session_id, turn_seq, role)`로 구분한다. loadContext는 낮은 turn_seq의 완료 턴을 읽는다. 복구 시 afterSeq 이후 신규 턴과 별도로, 이미 수락된 요청의 최신 결과를 요청 ID로 동기화하거나 세션 최신 50턴을 upsert하는 계약을 둔다. 50개 초과는 명시적 cursor/hasMore로 이어 받는다. 이벤트 커서와 턴 순번을 분리해도 되지만 별도 이벤트 저장소는 필수가 아니다.

### F2. Major · failed 동일 ID 재전송과 실패 상태 복구가 정의되지 않음 [R2][R8]

- **위치:** 설계:201~214, 247~248, 284, 288~289
- **문제:** 재전송 가능/retryable로 표시하면서 멱등 규칙은 completed와 processing만 다룬다. failed는 unique 제약 때문에 새 삽입도 불가능하다. 완료 트랜잭션 실패 시 user가 processing으로 남으면 duplicate는 영원히 완료를 기다릴 수 있다.
- **근거:** 재시작은 processing을 failed로 바꾸지만 그 요청을 재실행/오류 재발송하는 규칙이 없다. 재실행하면 `UNIQUE(user_message_id)` trace의 이전 실패 기록을 갱신할지 추가할지도 미정이다. 실패 상태의 retryable 값과 사용자 오류 설명을 복구할 저장 계약도 불완전하다.
- **제안:** failed 동일 ID는 저장된 최종 오류를 재발송하고 사용자가 새 clientMsgId로 재시도하는 단순 정책, 또는 원자적 failed→processing 재실행 정책 중 하나를 선택한다. 전자는 멱등성을 유지하기 쉽다. 새 요청 재시도라면 원래 요청과의 관계를 필요 범위에서 표시한다. 저장 실패는 별도 실패 전이를 시도하고 이것도 실패하면 해당 세션 진행/복구 정책을 정한다. pending 동기화에는 실제로 오류를 표시할 정보를 포함한다.

### F3. Major · 큐 초과 시 “저장 안 함”과 예약 후 ack 흐름이 상충 [R9]

- **위치:** 설계:78~79, 212, 249, 287
- **문제:** 흐름은 DB 메시지를 예약하고 ack한 뒤 큐에 넣지만, 실패표는 큐 초과를 ack QUEUE_FULL 및 저장 안 함으로 규정한다. 어떤 순서를 따라야 하는지 정할 수 없다.
- **근거:** 동시에 여러 소켓이 요청하면 단순한 사전 queue.length 검사로는 예약 중 증가하는 대기 수를 통제하지 못한다. 먼저 ack하면 동일 요청에 accepted와 QUEUE_FULL이 모두 관측될 수 있다.
- **제안:** 단일 프로세스의 세션별 수락 임계 구역에서 멱등 조회→큐 슬롯 예약→DB 원자 예약→enqueue→ack 순서를 정한다. 중복 조회는 큐가 가득 차도 결과를 반환하고, DB 예약 실패 시 슬롯을 되돌린다. 큐 거절은 DB 삽입/seq 할당 전에 끝내거나, 저장하기로 바꾼다면 failed 기록 정책과 표를 함께 맞춘다.

### F4. Major · 빈 B·전체 deadline·저장 오류의 경로 의미가 불명확 [R2][R15]

- **위치:** 설계:60, 67~70, 79, 89~120, 284~288
- **문제:** B 후보 0개는 외부 장애가 아닌데 “전부 실패” 판단에서 어떻게 제외하는지 없다. FAQ 확정 시 B를 무시한다고 해도 전체 기한 초과를 최우선 오류로 처리하면 느린 B 때문에 FAQ가 실패할 수 있다. AbortSignal만 넘기는 계약은 실제 기한 초과를 강제하는 방법과 저장 기한을 설명하지 않는다.
- **근거:** “메시지 전체 8s”와 큐 이후 handle 8s가 병존하여 세션 큐 대기를 포함하는지 불명확하다. B 작업을 모두 기다리는지 A 완료 후 FAQ로 조기 종료하는지도 없다. 저장 실패는 INTERNAL인데 규칙표 1은 기한 초과를 모두 JEV_UNAVAILABLE로 취급한다.
- **제안:** `B.empty`, `B.succeeded`, `B.failed`를 구분하고 후보 0개는 fallback으로 처리한다. FAQ가 확정되면 B 기다림을 종료/취소하고 완료 저장으로 진행할지 명시한다. 8초의 시작 시점·큐 대기 별도 상한·DB 저장 범위를 정하고 어댑터의 timeout/abort 및 늦은 완료의 이중 저장 방지를 검증한다. 공급자 실패·처리 기한·DB 오류의 종료 코드와 상태를 일관되게 매핑한다.

### F5. Major · 평가 스키마와 지표로 안전한 답변 여부를 판별할 수 없음 [R7][R4]

- **위치:** 설계:107, 256, 302~315, 340~341
- **문제:** `reference`는 문서 원문을 보여주지만 “답변 보류”에만 넣어 오답 자동응답률에서 제외한다. 주입·모호·범위밖의 “답변하지 않으면 통과”는 어떤 route/내용이 통과인지 없고, `blocked`·`error`는 보류율에도 빠져 있다. 따라서 시스템이 오류로만 종료하거나 불확실 문서를 보여줘도 일부 안전 지표가 좋게 나올 수 있다.
- **근거:** expect에는 route·FAQ/청크 ID만 있고 복수 청크 중 정답·오답 혼합, 필요 조항 누락, 계산 질문의 연락처 부가 규칙을 판정할 구조가 없다. 의도 정확도/검색 recall이 일부 문제를 잡아도 최종 답변 지표의 빈틈은 남는다. “정상 ERP 질문 + 주입 지시”는 지시를 무시하고 정상 답을 주는 것이 적절할 수 있어 주입 유형 전체 답변률 0%와도 충돌한다.
- **제안:** 평가 유형별 허용 결과와 금지 노출, 허용/필수 source 집합·FAQ 및 내용 판정 방법을 정의한다. 정상 in-scope 표본의 정답 제공률·보류율·장애율을 따로 측정하고 reference의 잘못된 문서 제시를 별도 실패로 센다. injection은 단순 답변 여부 대신 공격 목표 달성/금지 행동 여부로 판정하고 정상 부분 응답 허용 사례를 구분한다. threshold·영어/한국어 템플릿 선택은 tune에서만 수행하고 holdout은 최종 검증용으로 잠근다. 60건 holdout의 관측 결과를 운영 정확도 보장으로 표현하지 않는다.

### F6. Major · 계산 질문·상충 규정에 대한 안전 규칙이 Router에 연결되지 않음 [R4]

- **위치:** 설계:105~114, 169~175, 294, 303~304, 328
- **문제:** “계산이 필요한 질문은 담당부서 안내”라고 정했지만 질문 종류에는 계산 필요 플래그가 없고 intent/relevant만으로 이를 보장하기 어렵다. 높은 관련도를 받은 서로 다른 규정 최대 2개를 모두 보여줄 때 충돌·예외 조건 처리도 없다.
- **근거:** “이번 달 3회 사용했는데 남은 한도는?”은 regulation으로 분류될 수 있어 114행을 실행할 입력이 없다. number_date 평가 태그는 런타임 판단 값이 아니다. 높은 관련도는 두 규정이 서로 양립함을 의미하지 않는다. account_access는 단순 비밀번호 정책 질문과도 겹치므로 intent만으로 규정 전체를 구분하지 못한다.
- **제안:** MVP에서는 regulation 답변 모두에 계산하지 않는다는 안내/담당부서 확인을 일관되게 붙이는 등 보수적인 코드 규칙을 택하거나 계산 필요 판단을 명시적으로 추가한다. 샘플 청크에 적용 조건·예외를 함께 담고 중복/상충 근거 처리 규칙을 정한다. 충돌 판정용 새 모델 호출을 무조건 추가할 필요는 없다. 문서 구성과 보수적 안내로 해결할 수 있다.

### F7. Minor · ContextBuilder 보완이 검색 후보 품질까지 해결하지 않음 [R5]

- **위치:** 설계:82, 85~87, 134, 154~175, 312
- **문제:** 문맥을 Jev에 줘도 BM25 후보에 필요한 문서가 없으면 복구할 수 없다. 이전 사용자 문장을 무조건 0.5 가중치로 넣는 규칙은 주제 전환 때 불필요한 후보를 올리고, assistant가 제시한 메뉴를 가리키는 후속 질문은 검색어에 해당 메뉴가 없다.
- **근거:** 예시 추론: assistant가 “경비 정산 메뉴”를 안내한 후 “거기서 취소는요?”라고 물으면 최신 user 두 문장만으로 메뉴를 특정하지 못할 수 있다. 실제 recall 하락은 아직 측정되지 않았다.
- **제안:** 현재 입력 우선 검색과 제한된 문맥 검색의 후보 합집합 등 단순한 규칙을 비교하고 followup/주제 전환의 Recall@5/@8을 따로 본다. 후보를 얻지 못했을 때 이전 후보/출처 활용 또는 clarify로 종료하는 정책을 정한다. LLM 질문 재작성기를 MVP에 추가할 필요는 없다.

### F8. Major · 설정 스냅샷·버전 정리와 trace 재현의 계약 누락 [R14]

- **위치:** 설계:68, 83, 126, 188~216, 270~271, 334~338
- **문제:** 최근 10개 지식 버전만 유지하면서 대화/trace는 90일 보관한다. 잦은 import 시 trace가 참조하는 본문·FAQ를 잃는다. policy·intents·helpdesk가 DB/인덱스와 같은 스냅샷에 포함되는지도 없다.
- **근거:** trace의 후보 hash와 context turn ID는 내용을 복원하지 못한다. Retriever.version은 정의돼 있지만 다른 포트/Answerer가 동일 버전 FAQ/원문을 읽는 방법은 없다. template_version은 manifest와 코드 상수 두 곳에 존재한다. 이전 버전 삭제 시 FK 참조를 막을지 cascade할지도 미정이다.
- **제안:** domain-pack의 지식+정책+intents+연락처를 불변 실행 스냅샷으로 묶어 한 메시지에 전달하고 source FK는 같은 version_id의 chunk를 참조하게 한다. trace 또는 진행 중 작업이 참조하는 버전은 유지한다. 정책만 포함된 snapshots를 trace에 남기는 경우에도 실제 문서/FAQ 보존 기간을 맞춘다. template_version의 기준은 코드 상수로 두고 manifest 값은 호환성 검사 용도로 정의한다. MVP에서 버전 삭제를 미뤄도 된다.

### F9. Minor · 섹션 5 화면의 데이터 소스와 관리 요청 제한 누락 [R17]

- **위치:** 설계:249, 253~271
- **문제:** 현재 policy·모델·템플릿 표시와 평가셋 내보내기의 조회/실행 계약이 없다. “다시 가져오기”는 DB active로 인덱스를 reload하는 동작인데 파일 import와 혼동할 수 있다. review/reload rate limit도 없다.
- **근거:** REST 목록은 지식/대화/trace만 제공하며 설정 조회와 export가 없다. knowledge:import는 CLI인 반면 UI는 reload만 호출할 수 있다.
- **제안:** MVP에는 인증된 읽기 전용 설정 조회 하나를 추가하거나 화면에서 제거한다. export는 CLI로 할지 UI 다운로드로 할지 결정하고 검수자 권한·범위·스키마를 정한다. 버튼은 “활성 지식 인덱스 다시 로드” 등 실제 동작을 표시하고 reload 단일 실행·관리 작업 제한을 명시한다. 문자 수의 기준과 공백/ID 크기는 zod 계약 작업에 포함한다.

### F10. Minor · 미래 LLM 흐름과 독립 holdout 작업이 MVP 범위를 넓힘 (YAGNI)

- **위치:** 설계:25, 45, 69, 106, 241, 267~271, 302, 352
- **문제:** 섹션 9는 LLM 구현체 제외인데 구조에는 LLM 구현체가 있고 delta/llm 경로가 MVP 계약에 포함돼 있다. 구현 범위를 오해하면 현재 사용하지 않는 스트리밍 처리까지 만들 수 있다. “Codex가 별도 작성”을 합격 조건으로 박아 두면 검토 역할·도구 가용성과 평가 데이터 생성이 불필요하게 결합된다.
- **근거:** 현재 요청은 최종 검토 결과 파일 작성만 승인하며 holdout 작성은 요청 범위 밖이다. core 포트는 필요하지만 미사용 LLM 어댑터·스트리밍 E2E까지 구현할 이유는 없다. 평가의 독립성은 특정 에이전트 이름이 아니라 분리 절차로 달성한다.
- **제안:** MVP Answerer는 Extractive만 구현하고 LLM/delta는 예약된 향후 계약 또는 문서상 확장으로 명시한다. 미사용 어댑터와 UI 스트리밍 상태는 구현 계획에서 제외한다. holdout은 “튜닝 담당과 분리된 작성·검수, 임계값/템플릿 선택에 미사용”으로 정의하고 별도 작업으로 배정한다. 작은 가상 MVP에는 지식 이력의 GC, 별도 설정 화면·검수 queue API보다 기본 검수 목록과 CLI export로 시작해도 된다. 제한기·멱등성·권한·core 포트는 현재 요구이므로 YAGNI로 제거하지 않는다.

### F11. Minor · DevAuthProvider와 브라우저 토큰의 MVP 운영 조건 불명확 [R11]

- **위치:** 설계:222~226, 271, 275, 347~349
- **문제:** 하나의 dev 토큰은 모든 역할을 주지만 반환 userId가 없고 dev 활성화를 AUTH_MODE 값만으로 통제한다. 브라우저 저장 매체/삭제와 세션 권한 철회 시점도 없다. 단일 공유 계정이면 사용자당 제한·본인 세션 분리가 사용자별로 동작하지 않는다.
- **근거:** 가상 데이터용 내부 테스트라면 공유 admin 계정은 허용 가능한 단순화이나 이를 일반 사용자 인증 동작으로 검증했다고 볼 수 없다. 현재 userId 기반 소유권/제한 테스트는 별도 가짜 principal이 필요하다.
- **제안:** dev는 고정 테스트 userId를 쓰는 공유 관리자 계정임을 명시하고 운영 환경에서 AUTH_MODE=dev면 시작을 거절한다. 토큰은 기본 메모리/세션 한정으로 두거나 영속 저장 선택·로그아웃 삭제를 정한다. 일반 사용자 소유권/역할 테스트는 서로 다른 principal로 수행한다. 실사용 AuthProvider에는 만료 검증과 철회/역할 변경 시 연결 종료 또는 이벤트별 재검증 정책을 출시 조건으로 포함한다.

## 구현 계획으로 넘어가기 전 확인할 결정

1. **F1:** 요청 순서, assistant와의 관계, 이력 로딩과 완료 재동기화를 한 계약으로 확정한다.
2. **F2·F3:** failed 재시도와 큐 슬롯/DB 예약의 수락·거절 순서를 확정한다.
3. **F4:** 빈 B, FAQ 조기 완료, 8초의 적용 범위와 오류 코드/영속 종료 상태를 확정한다.
4. **F5·F6:** reference·공격·오류의 평가 판정과 계산/충돌 근거에 대한 실제 런타임 규칙을 확정한다.
5. **F8:** 구현 계획에 실행 스냅샷 범위와 참조된 지식 버전 보존을 필수 작업으로 포함한다. 나머지 Minor 항목은 범위 축소 또는 구체화 작업으로 반영한다.

실사용 출시 판단은 별개다. 위 계약을 정리하면 가상 데이터 MVP 구현 계획은 Go로 전환할 수 있지만, 실제 AuthProvider·개인정보/외부 전송 정책·실제 규정 평가·저장소 공개 범위에 대한 349행 조건을 충족했다고 볼 수는 없다.
