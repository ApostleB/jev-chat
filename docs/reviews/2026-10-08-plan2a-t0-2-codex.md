## AbortSignal.any/timeout 강제 GC 확인

모든 재현은 **Node 22.14.0 --expose-gc**로 실행했다. 참조되는 setInterval로 프로세스를 유지하고, 25ms 간격으로 GC를 호출했다. 따라서 timeout 타이머의 unref 때문에 프로세스가 먼저 종료된 현상과 구분했다. 300ms·3초·8초를 검사했고, 각 기한 이후 1.2초까지 관측했다.

| 형태 | 300ms | 3초 | 8초 |
|---|---|---|---|
| `any([controller.signal, AbortSignal.timeout(ms)])`, timeout 원본 별도 유지 없음 | 1.5초에도 미발화 | 4.2초에도 미발화 | 9.2초에도 미발화 |
| `linkedController(AbortSignal.timeout(ms)).signal`만 유지 | 동일하게 미발화 | 동일하게 미발화 | 동일하게 미발화 |
| 부모 timeout 신호를 강하게 유지한 linkedController | 약 302ms abort | 약 3002ms abort | 약 8001ms abort |
| 실제 ChatEngine에 timeout을 **인라인 인자로 전달**, A 즉시 완료/B 대기 | 약 302ms 종료 | — | 약 8002ms 종료, B abort 확인 |

8초 엔진은 부모 신호를 별도 배열에 유지한 대조군도 약 8002ms에 종료했다. 첫 검사 후 인라인 인자를 직접 넘기는 형태로 다시 실행해 호출자 로컬 변수의 신호 참조가 결과를 가리는 경우를 줄였다. 실제 SDK 경로의 별도 8초 검사에서도 동일하게 기한 전파가 성공했다.

**결론:** 구현자가 보고한 인라인 timeout 소스의 GC 관련 미발화는 재현됐다. 그러나 **현재 ChatEngine의 운영 형태에서 엔진 기한이 B로 전파되지 않는 현상은 재현되지 않았다.** 엔진은 부모 signal을 이후 race/Answerer/audit에서도 사용하고, pending 엔진 실행 중 부모 참조를 유지한다. SDK의 수동 타이머는 timer callback이 timeout controller를 유지하므로 해당 미발화 형태를 피한다. 이것은 이 코드/Node 버전/재현 조건에서의 확인이며, 모든 조합·다른 런타임의 안전성을 보장하는 주장은 아니다.

### T1. Minor · linkedController 단독 사용은 timeout 부모 참조 수명에 의존

- **위치:** `jev-chat-api/src/core/engine/abort.ts:23~26`, `engine/abort.spec.ts`.
- **문제:** helper 자체는 부모 신호의 강한 참조를 반환 객체에 보존하지 않는다. 엔진 외부에서 timeout을 인라인으로 넘겨 결과 signal만 유지하면 이번 Node 버전에서 기한 미발화가 발생한다.
- **근거:** 위 강제 GC 재현에서 300ms/3초/8초 모두 해당 형태가 미발화했다. 반면 현재 엔진과 실제 SDK 경로는 부모 기한을 지켰다. 따라서 **현재 엔진의 Major 장애로 상향하지 않는다**.
- **제안:** helper가 부모 참조 수명을 보장하도록 하거나 사용 제약을 명시한다. repo 회귀 테스트에 `--expose-gc` 별도 프로세스의 인라인 부모/부모 유지/실제 엔진 대조를 추가한다. 현재 synchronous 부모 AbortController 1000개 테스트만으로 timeout GC를 검증했다고 보지 않는다.

### T3. Minor · 재시도 sleep 완료 후 abort 리스너 잔존

- **위치:** `jev-chat-api/src/adapters/jev/typesafe-judge.ts:34~39`.
- **문제:** timer로 sleep이 정상 종료돼도 등록한 abort listener를 제거하지 않는다.

- **제안:** 정상 완료와 abort 양쪽에서 listener/timer를 정리한다. 같은 신호를 재사용하는 테스트와 8개 B 동시 재시도에서 listener 정리를 확인한다.
