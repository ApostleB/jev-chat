## 지적

### F1 — Major · 새로고침 후 resume ack 전에 온 완료 이벤트가 유실된다

- **위치:** `jev-front/src/lib/chat-client.ts:118`, `jev-front/src/lib/chat-client.ts:174`, `jev-front/src/lib/turns.ts:93`, `jev-front/src/hooks/use-chat.ts:15`.
- **문제:** 저장된 sessionId로 새로고침 후 복원할 때 ChatClient는 대상 세션을 알고 있지만 리듀서의 `state.sessionId`는 최초 hydrate까지 `null`이다. 이 사이 수신한 done/error/trace는 다른 세션 이벤트로 간주하여 버린다. 이력 응답에 아직 processing인 턴이 들어 있으면, 이미 완료된 턴이 화면에서는 계속 처리 중으로 남는다.
- **근거:** 서버는 권한 확인 → room 참여 → 이력 조회 순서다. 따라서 조회된 processing 스냅샷의 ack보다 완료 이벤트가 먼저 전달되는 경합은 허용된 동작이다. 실제 ChatClient와 turnsReducer를 연결한 임시 테스트에서 `resume 시작 → done·trace 수신 → processing 이력 ack` 순서를 재현했다. 최종 상태는 ready지만 턴은 processing, 답변과 trace는 없었다. 세션 준비 후 chat:send ack보다 done이 먼저 오는 기존 테스트만으로는 이 경우를 검증하지 못한다.
- **제안:** 동기화 세대·대상 sessionId별로 검증된 이벤트를 임시 보관하고 성공 ack의 hydrate 후 적용한다. NOT_FOUND/FORBIDDEN, 새 세션 전환, close 시 이전 버퍼를 폐기한다. 또는 복원 대상 세션을 리듀서에 먼저 설정하되 동일한 세대·권한 실패 정리와 terminal 우선 병합을 보장한다. done/error/trace 각각 및 이전 세션 이벤트 배제 회귀 테스트를 추가한다.

### F2 — Minor · 로그아웃의 query 취소가 실제 HTTP 요청에는 전달되지 않는다

- **위치:** `jev-front/src/App.tsx:27`, `jev-front/src/lib/api-client.ts:18`, `jev-front/src/lib/api-client.ts:29`, `jev-front/src/lib/use-cursor-list.ts:12`.
- **문제:** `cancelQueries()`와 캐시 초기화는 수행하지만 queryFn의 AbortSignal을 ApiClient와 fetch에 전달하지 않는다. 계획 U6의 진행 중 요청 취소는 네트워크 수준에서 구현되지 않았다.
- **근거:** 실제 QueryClient와 ApiClient를 사용한 임시 테스트에서 query 취소 후에도 fetch에 전달된 `signal`이 없음을 확인했다. 캐시는 비워졌으므로 이 사실만으로 이전 사용자 데이터가 다시 표시된다고 판정하지 않는다. 기존 App 테스트도 응답 완료 후 로그아웃을 검사해 실제 abort 여부는 확인하지 않는다.
- **제안:** GET 요청 옵션에 signal을 전달하고 각 queryFn의 signal을 연결한다. 지연된 fetch가 로그아웃·토큰 교체 시 abort되는지 검사한다. 진행 중 mutation은 query 취소와 별개이므로, 늦은 toast 등 인증 세대가 지난 UI 콜백도 차단한다. 이미 서버에 도착한 변경 요청까지 취소된다고 가정해서는 안 된다.

### F3 — Minor · retryAfterMs는 표시하지만 자동 재시도는 무시한다

- **위치:** `jev-front/src/main.tsx:7`, `jev-front/src/lib/api.ts:13`.
- **문제:** REST 오류 안내에는 retryAfterMs가 반영되지만 전역 query 설정은 오류 종류와 관계없이 `retry:1`이다. 서버가 제시한 대기 시간이 지나기 전에 자동 요청이 다시 나가며 401/403도 재시도한다. P6의 status·retryAfterMs 기반 재시도 판단과 다르다.
- **근거:** 같은 QueryClient 설정과 실제 ApiClient를 사용해 429·retryAfterMs=60000 응답을 주면 **1000ms 뒤 두 번째 요청**이 발생함을 가짜 타이머로 확인했다. errorText 단위 테스트는 안내 문구만 검사하고 실제 재시도 시각은 검사하지 않는다.
- **제안:** retry/retryDelay를 status와 retryAfterMs에 따라 설정하거나 자동 재시도를 끄고 명시적 재시도 UI로 통일한다. 429/503 지연 및 401/403 재시도 금지를 검사한다.

이 적응 자체에는 지적 없음. 설치된 Base UI `.d.ts`의 Select `items`·nullable onValueChange, Dialog의 기본 초점 이동/복귀 계약과 컴포넌트 사용을 대조했다. cn 0.4.0은 설치 패키지 메타데이터와 타입 선언상 shadcn-ui/cn의 Tailwind 클래스 병합 함수이며 현재 사용 형태와 맞는다.
