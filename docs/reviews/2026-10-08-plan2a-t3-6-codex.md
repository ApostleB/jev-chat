## 잔여 지적

### R1. Minor · saveMs의 논리 tx 예산과 실제 저장 응답시간 상한은 구분 필요

- **위치:** `jev-chat-api/src/adapters/persistence/turn.repository.ts:116~126`, `turn.repository.spec.ts:85~99`.
- **문제:** maxWait/timeout 분할과 save_ms≥1000은 반영했지만 실제 Promise가 saveMs 이내 끝나는 것을 보장/검증하지 않는다. 코드 주석도 잠금 대기 중 reject가 늦을 수 있고 실제 시간 상한은 계획 2B에서 정한다고 명시한다.
- **근거:** 현재 느린 저장 테스트는 rejection/최종 rollback만 확인하며 elapsed 상한은 검사하지 않는다. 이 테스트도 이번에는 skip됐다. 이전 P5의 기본 5초 tx·늦은 완료 방지 문제와는 구분하여, **응답시간 SLA는 아직 미입증**으로 판정한다.
- **제안:** DB 준비 후 실제 11.8에서 락 획득·실행·rollback 시간과 최종 상태를 함께 측정한다. 필요한 DB/driver 쿼리 대기 상한과 2B 오류/슬롯 반환 정책을 확정한다. Promise.race만으로 SQL 취소를 보장한다고 표현하지 않는다. Task 5 전체 완료를 DB 없이 확정하지 않는다.

### R2. Minor · 파일 로드와 DB 로드의 문서/FAQ 순서가 달라 동점 검색이 달라짐

- **위치:** `pack-loader.ts:85~104`, `knowledge.repository.ts:83~85`, `snapshot.service.ts:29`; 계획 3 offline snapshot의 Retriever 구성.
- **문제:** 파일은 JSONL 입력 순서를 유지하고 DB는 id ASC로 정렬한다. BM25는 동점일 때 입력 순서를 쓰므로 같은 팩이라도 파일 기반 평가와 DB 기반 서비스가 다른 후보를 고를 수 있다.
- **근거:** 실제 데이터 없이 합성 동일 문서 두 개를 z→a 순서로 넣으면 k=1 결과가 z, DB의 id ASC를 모사해 a→z로 넣으면 a였다. 현재 계획 2A의 정렬 코드는 그대로 구현한 것이므로 구현자의 임의 변경은 아니다. 다만 후속 품질 평가와 서비스의 일관성 문제로 남는다.
- **제안:** 모든 로드 경로에서 같은 canonical 순서를 적용하거나 원본 순번을 DB에 저장한다. DB collation과 JS 정렬 기준도 맞춘다. 동점/후보 k 절단을 포함한 파일→DB round-trip 검색 동일성 테스트를 추가한다. 실제 tune/chunks 데이터는 본 재현에 사용하지 않았다.

### R3. Minor · DB 동시성/rollback 테스트의 실패 주입과 대기 조건이 취약

- **위치:** `turn.repository.spec.ts:66~99`, `knowledge.repository.spec.ts:55~64`.
- **문제:** lock holder가 잠금을 얻었다고 100ms sleep으로 추정한다. 길이 초과에 의한 insert 실패는 strict SQL mode에 의존한다. 동시 예약 검사는 5개까지만 확인하고 동일 clientMsgId 충돌의 counter rollback을 직접 검사하지 않는다.
- **근거:** 느린 환경에서는 holder보다 complete가 먼저 실행될 수 있다. SQL mode가 달라 길이를 잘라 저장하면 기대한 insert 오류가 발생하지 않는다. 현 테스트는 아직 skip이라 조건이 실제 DB에서 성립하는지 확인하지 못했다.
- **제안:** FOR UPDATE 성공 후 barrier로 holder 준비를 알리고 나서 저장을 시작한다. SQL mode를 테스트 전제로 확인하거나 unique/FK 등 결정적인 실패 조건을 사용한다. 중복 요청 실패 후 next_turn_seq와 다음 정상 순번, 동일/다른 팩 동시 import, complete/fail 양쪽 경합을 실제 DB에서 확인한다.

### R4. Minor · 정수 토큰 검증이 안전 정수/DB 범위까지 보장하지 않음

- **위치:** `jev-chat-api/src/adapters/jev/sdk-transport.ts:59`, `prisma/schema.prisma`의 MessageTrace.totalInputTokens Int.
- **문제:** Number.isInteger는 1e20 같은 안전 정수 범위 밖의 큰 값도 허용한다. 정상 응답처럼 받아 trace 합산 후 DB Int 저장에 맞지 않을 수 있다.
- **근거:** 가짜 fetch로 input_tokens=1e20을 전달한 추가 재현에서 Judge ok=true였다. T2가 지적한 소수/빈 문자열은 현재 거절됐지만 원 리뷰의 안전 정수 제안까지 충족한 것은 아니다. 실제 공급자에서 이런 값이 반환됐다는 근거는 없다.
- **제안:** Number.isSafeInteger와 합당한 token count 범위를 검증하고, 합산값의 저장 타입 계약을 확인한다. 초과 메타데이터는 invalid_response/재시도 없음으로 처리하는 테스트를 추가한다. 정상 호출 한도 안의 값은 그대로 허용한다.
