- 대상: `docs/superpowers/specs/2026-10-08-jev-chat-design.md` 섹션 1~4. 섹션 0은 관련 결정의 문맥으로만 참조했다.

- 확인 범위: 로컬 설계와 추적 파일 목록, TypeSafe 공식 문서. 코드가 없어 구현 취약점이나 테스트 통과를 주장하지 않는다. 아래 위험 시나리오는 설계에서 도출한 추론이며 실제 장애·침해가 확인된 것은 아니다.

## 1. Major · 외부 API 전체 호출량과 토큰 제한 제어 누락

- **위치:** 설계:57~59, 164 (섹션 1·4)
- **문제:** 메시지마다 A 1건 + B 10~12건을 동시에 발사하지만 사용자별 분당 제한과 세션 큐만 있다. 사용자/세션이 달라지면 제한을 합산하지 못한다. “왕복 1회분 지연”도 큐 대기·재시도·가장 느린 B 응답 때문에 보장되지 않는다.
- **근거:** 후보 12개 기준 7개 메시지의 동시 시작은 `7 × 13 = 91`요청이다. 공식 제한은 현재 80요청/초와 100K토큰/초이며 둘 중 하나를 넘겨도 429가 발생하고, 제한은 변경될 수 있다. [Models](https://docs.typesafe.ai/models)
- **제안:** 공급자 자격증명을 공유하는 호출 전체에 설정 가능한 요청/토큰 예산, 동시 실행 상한, 유한 대기열과 총 처리 기한을 적용한다. SDK 내부 재시도도 예산에 포함하거나 재시도를 한 계층에서 관리한다. 지연 표기는 이상적인 병렬 실행 가정으로 한정하고 처리량·대기시간 목표를 별도로 정의한다.

## 2. Major · A/B 일부 실패의 답변·종료 정책 누락

- **위치:** 설계:57~66, 120, 134~135, 152, 164
- **문제:** A 실패, B 일부 실패, B 전체 실패에서 어느 결과로 답할지와 큐를 언제 해제할지가 없다. 하나의 실패로 성공한 FAQ까지 버리거나, 범위 판단 실패 상태에서 문서 답변을 반환할 수 있다.
- **근거:** 정상 분기만 있으며 `JEV_UNAVAILABLE` 코드와 단일 `error` 필드로는 청크별 성공/실패를 구분하기 어렵다. 공식 API는 429 외에 529 과부하와 백오프 처리도 명시한다. [API reference](https://docs.typesafe.ai/api)
- **제안:** 호출별 완료 상태·재시도 횟수·기한을 기록하고 A 실패 시 안전한 종료, FAQ가 확정된 경우 B 실패 허용 여부, B 부분 성공의 최소 근거 조건을 정의한다. 관련 문서 없음과 공급자 장애를 구분하며 모든 종료 경로에서 다음 세션 작업을 진행시킨다.

## 3. Major · 범위밖 판단이 불확실하면 FAQ/B로 통과

- **위치:** 설계:61~65, 83~90
- **문제:** `out_of_scope`가 0.69여도 FAQ 0.71 또는 청크 0.51이면 답변한다. 범위 안임을 확인하는 조건은 없다. 헬프데스크 안내는 반대로 intent 확률 조건 없이 붙는다. 인사와 ERP 질문이 섞인 입력의 우선순위도 불명확하다.
- **근거:** 현재 분기는 높은 확률의 범위밖만 차단하고 나머지를 모두 답변 후보로 넘긴다. `P`가 선택 옵션의 확률인지 두 차단 옵션의 확률 합인지도 명시되지 않았다.
- **제안:** 범위 안/밖/불확실의 정책을 명시하고 불확실할 때 재질문 또는 안내로 종료한다. 선택 옵션 확률과 합산 확률을 구분하고 혼합 질문의 기준을 criteria에 넣는다. 헬프데스크 분기도 별도 확률 기준을 적용한다. 이 분류를 접근 권한 검사로 사용하지 않는다.

## 4. Major · 불확실한 Noul을 규정 답변 근거로 승인

- **위치:** 설계:63, 109~119
- **문제:** 0.5는 긍정·부정이 같은 가능성인데 바로 원문을 답으로 내보낸다. 임계값을 추후 조정한다는 선언만으로 잘못된 규정 안내의 허용 수준을 결정할 수 없다.
- **근거:** Noul 문서는 중간값을 불확실성으로 설명하며 잘못된 긍정의 비용에 따라 임계값을 높이거나 중간 영역을 별도 처리하도록 안내한다. [Noul](https://docs.typesafe.ai/primitives/noul) Choice의 `confidence`는 선택 확률과 다른 분포 통계이며, 불확실할 때 행동을 보류하는 경로가 제시된다. [Confidence](https://docs.typesafe.ai/confidence)
- **제안:** FAQ 확률·Choice confidence·Noul 승인 기준을 구분한다. 임계값 주변에는 재질문/담당부서 연결 구간을 두고, 경계값·동점·여러 청크의 모순 처리와 실제 사용 전 품질 합격 기준을 정의한다. confidence를 함께 쓴다는 이유만으로 정확성이 보장된다고 해석하지 않는다.

## 5. Major · 이어지는 질문의 문맥이 검색·FAQ·B에서 일치하지 않음

- **위치:** 설계:56, 69, 83, 99~100, 106~112
- **문제:** A에는 최근 3턴을 넣지만 B는 현재 question과 passage만 받는다. FAQ 지시에는 문맥 사용 기준이 없고 검색에는 직전 사용자 메시지만 들어간다. “그건 어디서 신청해요?”는 intent를 이해해도 B가 대상을 알 수 없으며, 새 주제로 바뀌면 과거 검색어가 잘못된 후보를 올릴 수 있다.
- **근거:** 참조 해석 지시는 intent에만 명시돼 있다. 최근 3턴에 assistant 답변·출처가 포함되는지, 큐 대기 중 어느 시점의 이력을 쓰는지도 없다.
- **제안:** 턴의 정의와 처리 시작 시 확정된 이력 범위를 정하고, 동일한 질문 문맥을 Retriever·FAQ 판단·각 B 판단에 전달한다. 주제 전환·대명사 미해결·두 개 이상의 가능한 참조는 재질문으로 처리한다. 모델이 질문을 새로 생성해야 한다고 가정하지 말고 필요한 원문 이력/참조 정보를 명시적으로 전달한다.

## 6. Major · FAQ “완전한 답” 판단에 실제 답과 적용 조건이 없음

- **위치:** 설계:54, 99~100, 129~130
- **문제:** 선택 기준은 FAQ summary뿐인데 판정은 직원 질문에 완전히 답하는지이다. 요약이 “경비 한도 안내”여도 실제 answer가 출장비만 다루면 회식비 질문에 잘못 선택될 수 있다. 상위 5개에 정답이 없으면 모델이 복구할 수도 없다.
- **근거:** Choice는 제공한 후보 중에서 선택한다. 공식 문서는 후보 밖 입력용 옵션을 권고한다. `none`은 이 요구에 맞지만 후보 누락을 복구하지는 않는다. [Choice](https://docs.typesafe.ai/primitives/choice)
- **제안:** A state에 FAQ별 실제 답변과 적용 조건을 포함하고 criteria에서 해당 레코드를 명확히 참조한다. summary만 사용하려면 완전성 판정에 필요한 조건을 모두 담는 스키마를 정의한다. FAQ Recall@5와 문서 Recall@12를 별도 평가하고 후보 부족·0개인 경우도 계약에 포함한다.

## 7. Major · 한국어 평가의 실사용 전 합격 기준 누락

- **위치:** 설계:118~121, 138 (관련 배경:33)
- **문제:** 영어/한국어 질문 비교와 평가셋 조정은 선언돼 있으나 실제 운영 허용 기준이 없다. 가상 샘플과 운영 중 review만으로는 한국어 ERP 용어·숫자·예외 조항의 위험을 입증할 수 없다.
- **근거:** 공식 문서는 영어에서 가장 정확하며 CJK를 동등하게 처리하지 못한다고 명시한다. [Models](https://docs.typesafe.ai/models) 알려진 한계에는 간접 참조·숫자·날짜·옵션 순서 영향이 포함된다. [Jev 1.13 jaggedness](https://docs.typesafe.ai/model-jaggedness/jev-1.13)
- **제안:** 섹션 6에서 구현 전에 고정할 검증셋과 합격 조건을 연결한다. 실제 사용 전에는 승인된 실제 규정 기반 한국어 질문, 부정문·유사 FAQ·범위밖·이어지는 질문·옵션 순서 변경을 평가하고 오답 자동 응답률/답변 보류율/검색 recall을 분리 측정한다. 임계값 튜닝셋과 최종 검증셋을 나눈다. 금액·기한 계산은 코드로 하거나 원문 안내 및 확인 요청으로 제한한다.

## 8. Major · 멱등성에 필요한 처리 상태·원자적 저장 계약 누락

- **위치:** 설계:66, 133~136, 148, 164
- **문제:** `(session_id, client_msg_id)` 유일성만으로 재전송 시 중복 판단·중복 assistant 생성·결과 유실을 막을 수 없다. 같은 ID에 다른 text가 오는 경우, ack 이후 프로세스 종료, DB 저장 일부 실패의 동작이 없다.
- **근거:** 처리 상태, user↔assistant의 유일 대응, 동일 요청의 결과 재사용 계약이 없다. trace는 양쪽 메시지 FK를 요구하지만 실패 시 assistant가 없는 상태는 표현되지 않는다.
- **제안:** DB에서 요청을 원자적으로 예약한 뒤 ack하고 accepted/processing/completed/failed 상태와 입력 일치 검증을 둔다. assistant와 trace의 중복을 막는 제약, 최종 답·trace·완료 상태의 트랜잭션, 기존 요청 재전송의 동일 messageId/결과 반환을 정의한다. 실패·중단 trace의 nullable FK 또는 별도 실행 모델도 정한다.

## 9. Major · 세션 순차 처리와 재시작 후 복구의 정의 누락

- **위치:** 설계:69, 132~135, 164 (관련 배경:31)
- **문제:** 큐가 세션별이라는 설명만 있고 다중 소켓 동시 전송의 순서·대기열 상한·재시작 복구가 없다. 시간만으로 턴을 정렬하면 같은 created_at에서 순서가 모호하다. 단일 PM2 인스턴스도 메모리 큐의 내구성을 보장하지 않는다.
- **근거:** 데이터 모델에 세션별 순번·작업 상태가 없고 큐에 DB 수락 순서와 연결된 계약이 없다.
- **제안:** 세션별 서버 수락 순번과 유일 제약을 두고 이를 이력·큐·이벤트의 순서 기준으로 사용한다. 컨텍스트는 직전 작업 종료 후 읽는다. 큐 상한·기한·실패 후 진행과 재시작 시 pending 작업 복구/명시적 실패 정책을 정한다. 영속 큐가 MVP에 과하면 재시작 시 실패 처리와 안전한 재전송을 명시한다.

## 10. Major · 재연결·ack 유실 시 결과 동기화 불가능

- **위치:** 설계:147~154, 164
- **문제:** history만으로는 처리 중 요청인지 완료된 요청인지 확인할 수 없다. 완료 직전 연결이 끊기면 `chat:done`을 다시 받을 계약이 없고, ack 전 실패는 messageId로 상관관계를 만들 수 없다. LLM delta는 중복/누락 감지 정보가 없다.
- **근거:** 이벤트에 sessionId·clientMsgId·순번이 없으며 상태 조회/결과 재전송과 성공·오류 ack 구분이 정의되지 않았다. 재전송 보장이 설계에 제시되지 않았다.
- **제안:** 재연결 시 마지막 순번 이후의 완료 결과와 pending 상태를 동기화하고 동일 clientMsgId 재전송을 결과 조회로도 사용한다. ack를 성공/오류 판별 가능한 형태로 만들고 clientMsgId를 돌려준다. 이벤트의 세션 식별·종료 상태·delta sequence를 정의하며 MVP에서는 최종 done으로 부분 텍스트를 교체하는 복구 정책을 명시할 수 있다.

## 11. Major · 인증 이후 객체 소유권·REST 역할별 권한 누락

- **위치:** 설계:132, 143~161
- **문제:** 연결 토큰 검증과 debug trace 제한만으로는 임의 sessionId/traceId 접근을 막을 수 없다. 세션 목록·이력·trace·review·지식 reload의 접근 정책과 토큰 만료 후 열린 연결의 동작이 없다.
- **근거:** 모든 대상 ID를 클라이언트가 제공할 수 있지만 `session.user_id` 소유권 검사나 REST 인증·관리 역할이 명시되지 않았다. 이는 설계 누락이며 구현된 권한 우회를 확인한 것은 아니다.
- **제안:** 모든 소켓/REST 작업에서 principal과 객체 소유권 또는 명시적 관리 권한을 확인한다. debug 열람, review 작성, knowledge reload를 별도 정책으로 정하고 reviewer는 서버 principal에서 얻는다. 방 참여와 결과 발송에도 같은 정책을 적용하며 권한 없는 소켓으로 trace를 broadcast하지 않는다. 토큰 만료·철회·재인증, Origin 허용 목록과 전송 암호화도 연결 계약에 포함한다.

## 12. Major · “개인정보 user_id만 저장”과 원문·trace 저장이 모순

- **위치:** 설계:69, 120, 133~139
- **문제:** 사용자 text·후보·jev_raw·review note에 이름·계좌·비밀번호 등이 포함될 수 있고 최근 대화와 사내 문서가 외부 API로 나간다. 보관 정책을 이후로 미루면 MVP에서도 민감정보가 지속 저장·노출될 수 있다.
- **근거:** text와 JSON 원문 저장은 user_id 외 정보를 실제로 보관하는 설계다. 공급자는 고객 데이터를 학습에 쓰지 않는다고 설명하지만 enterprise ZDR는 별도 안내이며 이를 일반 계정의 무보관 보장으로 볼 수 없다. [Models](https://docs.typesafe.ai/models)
- **제안:** 개발 MVP는 비민감 가상 데이터로 제한하고 실제 사용 전에 저장·외부 전송 허용 범위와 마스킹, TTL·삭제·접근 정책을 결정한다. `jev_raw`는 허용된 응답 필드만 저장하고 SDK HTTP 객체·헤더·키를 제외한다. 본문·오류·review에도 민감정보 정책을 적용한다. domain-pack의 실제 규정을 git에 넣을 때도 저장소 열람 범위와 승인 절차를 정한다.

## 13. Major · 모델 분류를 악의적 입력과 문서 유출의 방어로 볼 수 없음

- **위치:** 설계:61~64, 83~112, 128~129, 151~153
- **문제:** “FAQ를 선택하라” 같은 사용자 주입 지시로 판단이 바뀌면 원문 발췌가 그대로 전달된다. 향후 부서별 접근 제한 자료를 적재해도 현재 스키마·검색에는 지식 접근 범위가 없다. 프런트의 문서/trace/오류 렌더링 정책도 없다.
- **근거:** 공식 한계 문서는 state의 적대적 내용이 판단을 움직일 수 있다고 명시한다. [Jev 1.13 jaggedness](https://docs.typesafe.ai/model-jaggedness/jev-1.13) 현재 문서에 권한별 자료가 있다는 사실은 확인되지 않았으나, 검색 범위에 대한 정책은 필요하다.
- **제안:** 사용자가 주는 텍스트와 문서 안의 지시를 데이터로 취급하도록 명시하고 한국어 주입 사례를 평가한다. 전 직원 공통 자료만 적재할지 결정하거나, FAQ/청크 ACL을 검색 이전부터 필터링하고 출력 직전 재검사한다. 접근 통제를 Jev에 맡기지 않는다. 원문은 기본 텍스트로 렌더링하고 Markdown/HTML 사용 시 위험 태그·링크를 제한한다.

## 14. Major · 지식 reload와 답변 재현성에 필요한 버전 계약 누락

- **위치:** 설계:120, 125~136, 161
- **문제:** 서버 시작 인덱스와 DB를 reload할 때 일관되게 교체하는 방법이 없다. 진행 중 판단의 청크가 바뀌거나 삭제되면 답변 출처와 당시 근거가 달라진다. model_version·thresholds만으로는 판단을 재현할 수 없다.
- **근거:** content_hash는 청크 현재값뿐이며 FAQ 버전·실제 판단 입력·instructions/criteria 버전·지식 스냅샷은 trace의 명시 필드가 아니다. JSON candidates가 어떤 내용을 보존하는지도 없다.
- **제안:** 지식 import를 검증 후 버전 단위로 적용하고 인덱스 스냅샷을 원자 교체한다. 한 메시지는 하나의 지식 버전을 사용한다. trace에 후보 ID/hash, FAQ/문서 버전, 질문 템플릿 버전과 실제 입력의 허용된 스냅샷 또는 참조를 보존한다. 삭제된 출처와 review의 expected ID 처리, index 빌드 실패 시 이전 버전 유지도 정의한다.

## 15. Minor · core 이식성을 입증할 입출력·실행 포트 계약 부족

- **위치:** 설계:52, 66, 120, 143~154 (관련 구조:38~42)
- **문제:** 폴더 분리와 금지 import는 정했지만 ChatEngine.handle 입력·출력, 진행 이벤트, 저장·큐·인증 경계가 없다. core가 소켓 이벤트·Prisma JSON·TypeSafe SDK 응답형을 직접 쓰게 될 가능성은 현재 설계만으로 배제되지 않는다.
- **근거:** 흐름 설명은 core 수행과 transport 발송을 함께 적고 있으며 포트의 데이터 계약은 아직 없다. 실제 의존 위반은 확인되지 않았다.
- **제안:** core는 principal/context·메시지 DTO를 받아 도메인 결과/진행 상태를 내보내도록 한다. 앱은 zod 검증·권한 확인·DI·transport 변환을 맡고 adapters는 공급자/DB 변환을 맡는다. Repository·Judge·Retriever·Answerer의 최소 계약에 기한·취소·오류를 포함한다. 공급자 원본 trace는 외부 SDK 타입이 아닌 JSON 호환 감사 자료로 경계를 넘긴다. core를 NestJS 없이 호출하는 검증을 구현 완료 기준으로 둔다.

## 16. Minor · 발췌 답변의 근거 수와 저장 sources 의미가 모순

- **위치:** 설계:63, 68, 133, 151
- **문제:** 흐름은 상위 3개로 답변하지만 MVP는 1위 청크 원문이다. sources가 선택한 3개인지 실제 출력한 1개인지 불명확하면 사용자가 읽지 않은 근거를 인용한 것으로 보일 수 있다.
- **근거:** 두 설명에 Answerer별 계약이 없고 sources의 ID·버전·발췌 범위 스키마도 없다.
- **제안:** extractive는 승인된 1위만 답변/인용하고 llm은 최대 3개 근거를 전달하는 등 방식을 명확히 구분한다. sources는 실제 사용한 근거만 포함하고 ID·title·section·version/hash를 정의한다. 문서가 서로 모순되거나 예외 조항이 다른 청크에 있으면 안내를 보류하거나 관련 조항을 함께 보여준다.

## 17. Minor · 프로토콜 버전·검증·큐 과부하 에러 계약 미완성

- **위치:** 설계:143~164
- **문제:** protocolVersion을 받지만 불일치 처리와 서버 지원 범위를 정하지 않았다. 1,000자의 기준, ID/빈 문자열 검증, 모든 C→S·REST의 오류 ack, 과부하 시 재시도 시간이 없다. 세션 생성·review·reload는 chat 사용자 제한에 포함되는지도 불명확하다.
- **근거:** zod 공유는 선언돼 있으나 payload별 제약과 history 페이지네이션·실행 제한은 정의되지 않았다.
- **제안:** 이벤트별 성공/실패 스키마, 버전 협상 또는 거절 코드, 문자열/ID/JSON 크기 제한과 history cursor를 정한다. 유일 사용자 ID에 기반한 제한을 재연결 후에도 유지하고 session 생성·관리 API에는 별도 제한을 둔다. 큐가 가득 찬 경우 retryAfter와 명확한 오류를 반환한다. 금지된 역할의 요청은 인증 실패와 구별 가능한 권한 오류로 처리한다.

## 18. Minor · trace 원본 요구가 Noul 응답 형태와 맞지 않음

- **위치:** 설계:77, 106~120, 134~135
- **문제:** “확률 분포 전체, confidence”를 모든 응답에 기대하면 B Noul에 존재하지 않는 필드를 요구하게 된다. `relevant`가 API 응답 필드인지 도메인 매핑값인지도 명시되지 않았다.
- **근거:** 실제 Noul 답변은 `type`과 `noul`이며 별도 confidence가 없다. [Noul](https://docs.typesafe.ai/primitives/noul) Choice에는 choice/probabilities/confidence가 있다. [Choice](https://docs.typesafe.ai/primitives/choice)
- **제안:** 원본은 타입별 union으로 보관하고 `answers.relevant.noul`을 도메인 relevant 값으로 명시적으로 매핑한다. B별 청크 ID와 응답·usage·실제 model을 연결하고 전체 토큰 수는 A와 모든 B 요청을 합산한다. 파생 `1 - noul`은 원본 필드와 구별한다.

## 공식 문서 대조에서 지적 없는 항목과 해석 범위

- **Choice/Noul 정의:** 제시된 질문 객체의 type/instructions/criteria 형태, intent·faq의 Choice와 relevant의 Noul 선택은 공식 primitive와 일치한다. A의 두 질문을 한 요청에 넣는 방식도 일치한다. FAQ의 `none`은 후보 밖 답변을 위한 적절한 옵션이다. [Choice](https://docs.typesafe.ai/primitives/choice), [Noul](https://docs.typesafe.ai/primitives/noul)
- **요청 B:** 공식 rerank는 query-candidate 쌍마다 한 호출을 병렬 실행하고 Noul로 정렬한다. 따라서 후보별 호출 자체는 지적 없음. 다만 이것이 API가 강제하는 유일한 방식이라는 의미는 아니며, 같은 쌍에 대한 여러 판단은 한 호출로 묶을 수 있다고 문서도 설명한다. [Re-ranking](https://docs.typesafe.ai/cookbooks/rerank_typesafe)
- **Score:** 단계가 있는 정도 판단용이다. 현재 “직접 답하는가”라는 이진 판정에 Score를 사용하지 않은 것은 지적 없음. 부분/완전 답변의 정도를 따로 판단하려면 기술된 단계와 confidence가 있는 Score를 선택할 수 있지만, 값은 일반적인 0~1 확률이 아니며 단계에 따른 범위다. [Score](https://docs.typesafe.ai/primitives/score)
- **모델 고정:** `jev-1.13.0` 고정은 공식 권고와 맞다. 관련 배경 17행의 context 설명에는 총 64k 외에 state+가장 긴 질문 32k 제한도 반영해야 한다. 요청 크기 검증에는 두 제한을 모두 적용한다. [Models](https://docs.typesafe.ai/models)
- 공식 문서 목록은 [llms.txt](https://docs.typesafe.ai/llms.txt)로 확인했다. 일부 `.md` URL은 조회 도구에서 실패하여 동일 공식 사이트의 확장자 없는 페이지로 확인했다. 실제 계정 한도·한국어 정확도·SDK 동작은 API 키를 사용해 측정하지 않았다.
